## Стандарт записи знания

**Каждое утверждение имеет тип.** `C` — подтверждено текущим кодовым путём; `G` — закрыто конкретной программной регрессией; `P` — предел платформы из первичного источника; `H` — последствия требуют реального устройства. `C/H` не значит «ошибка уже случилась»: это видимое допущение с неизвестной частотой/эффектом. Для реального инцидента указывать exact build, OS/browser, firmware и первый расходящийся шаг, ссылаясь на observation в продуктовом контуре без копирования имени/контактов.

**Запись считается полезной, если она отвечает на пять вопросов:** какой механизм отказа; какой источник его подтверждает; где он в нашем коде; что уже защищено тестом; какой один эксперимент меняет решение. Нельзя добавлять ещё один framework/SDK только на основании «так принято». При смене версии браузера/пакета повторно открыть источник и поправить дату, не переписывая старую дату аудита.

**Приоритет зависит от стадии:** личный exact-build тест → новый изменённый кандидат → малая пользовательская волна → production. Для личного теста использовать короткий `PHYSICAL-TEST.md`, не весь атлас. На первом FAIL остановиться. Технические события помогают найти место разрыва, но `running`/HTTP 202/открытое письмо не являются человеческим outcome.

## Обслуживание корпуса

1. Новый проверенный платформенный факт → добавить первичный URL и дату в `sources.md`, затем уточнить один failure mode или решение.
2. Новый дефект из пользователя → сначала карточка в `product-experience`; в репо только обезличенный механизм, commit, regression, exact candidate и связь с наблюдением по ID.
3. После фикса → сменить статус `C/H` на `G` только при конкретном тесте и на `physical verified` только при отчёте с точным build/setup. Сохранять прошлые audit snapshots с датой вместо стирания истории.
4. Раз в месяц пройти высокоприоритетные `H` и устаревшие ссылки, убрать доказанно нерелевантное, объединить дубли. Git commit/push документации — обычный ручной, без cron/autocommit.

## Что уже отличается от прежних кратких обзоров

- Общий импорт preset JSON в шести страницах мутирует до полной валидации. В Biotron это также может рассогласовать форму и прибор.
- Общий `FileDropArea` недоступен обычной клавиатурой, не ограничивает размер и не сообщает ошибку FileReader.
- Для телеметрии явно описаны пропущенные события, неоднозначный порядок внутри секунды, доверие к build ID и реальная операция retention.
- Для `_headers` отделена live проверка применения от содержания CSP: текущая политика защищает от встраивания, но не задаёт script policy.

**Следующий вывод:** ни один обзор не исключает все будущие сюрпризы. Корпус предназначен для быстрого опровержения конкретных рисков и для выбора минимальных правок, а не для бесконечного добавления кода.
